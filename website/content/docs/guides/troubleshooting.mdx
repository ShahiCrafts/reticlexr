title: Troubleshooting
description: Symptom-by-symptom fixes for the problems developers actually hit with v1.0.0 — most trace back to a short list of known behaviours.
---

## AR won't start on my phone, but works on desktop localhost

Almost certainly the **secure context**. WebXR immersive AR requires
HTTPS (or `localhost`). A LAN address over plain HTTP loads the page but
session creation fails. Since 1.1.0, `checkSupport()` reports this
distinctly with the code `INSECURE_CONTEXT` (in v1.0.0 its `reason` did
not distinguish an insecure origin from an unsupported browser). Serve the page
over HTTPS — see
[HTTPS and phone testing](/docs/getting-started#https-and-phone-testing) —
or open this site's [live demo](/demo), which is already HTTPS.

## The session fails immediately on some Android devices

That was v1.0.0: session creation required `local-floor`, and devices
with immersive AR + hit-test but no `local-floor` failed outright.
Since 1.1.0, `local-floor` is optional — the engine falls back through
`local-floor` → `local` → `viewer`, so this failure mode is gone. If a
session still fails at creation, the device lacks `hit-test` or
immersive-AR support itself.

## `checkSupport()` says yes, but the native session fails later

On the native Android facade, `checkSupport` currently resolves
`{supported: true}` unconditionally — it never asks ARCore for real
availability. Gate your UI on it if you like, but handle `startSession`
failure as the real support test on Android. (The WebXR
`checkSupport()` used by `ARView`/the hook does perform a real check.)

## My model never appears (hook `placeModel`)

If you're calling the hook's `placeModel(modelUrl, position, rotation,
scale)`: both shapes work since 1.1.0 — arrays (position `[x, y, z]`,
rotation as a quaternion `[x, y, z, w]`, scale `[sx, sy, sz]`) or
`{x, y, z}` objects (rotation objects are Euler angles in radians),
normalised at the engine boundary. In v1.0.0 the engine wanted arrays
while the JSDoc described objects, and objects produced `NaN`
components and invisible models. If a model still never appears, check
for `NaN` in the values themselves. The facade's
`ARView.placeModel(url)` doesn't take transform arguments at all —
prefer it unless you need the engine-level control.

## `detectedPlanes` in the hook is always zero

Fixed in 1.1.0: the engine emits plane counts as numbers and the hook
now reads them as numbers (in v1.0.0 it read `.length` of the numeric
counts, so they always showed zero). The plane-listener payload is
`{type, total, horizontal, vertical}` — counts as numbers.

## `placeModel(url, {x, y})` ignores where I tapped

Fixed in 1.1.0: non-centre points run a real ray-based hit test (an
offset ray from the camera pose through the tapped point), so
tap-to-place lands where the user tapped, and everything built on it
(facade placement, the web `moveModel`) honours the point too. The
centre point keeps the fast viewer-ray path. In v1.0.0,
`hitTest({x, y})` ignored its coordinates and always returned the
centre-screen hit.

## My reticle setting keeps turning back on

Fixed in 1.1.0: the forced resets are gone — `showReticle: false` is a
user preference that survives session start, placement and removal
(v1.0.0 overrode it back to `true` at each of those moments).
`setReticleVisible(false)` still hides it immediately.

## Every tap throws `TypeError: options.modelUrl is not a function`

That was v1.0.0: `enableCustomization({ modelUrl })` expected a
**function**. Since 1.1.0 it accepts a plain string or a
`() => string` (use the function form when the URL changes between
taps), and placement failures are routed to `options.onError` instead
of being thrown through the tap handler. See
[Gestures](/docs/guides/gestures).

## Memory grows while users browse products

Largely fixed in 1.1.0. Removed models and plane visualisations are
now disposed — per-instance resources immediately; shared geometry and
cached textures when their cache entry is evicted or the engine is
disposed. Plane dots are a single `InstancedMesh` per plane instead of
one mesh per dot. The model cache is capped (20 models by default,
LRU — see the `modelCacheLimit` config) with a `clearModelCache()`
escape hatch, and `ARView.destroy()` performs a full engine teardown
including the renderer and GL context. In v1.0.0 none of this was
disposed and the cache never evicted. The remaining good practice is
unchanged: switch with `switchModel()` instead of repeated
`placeModel()` calls.

## `takeScreenshot` returns `CAMERA_CAPTURE_UNAVAILABLE`

The session has no WebXR camera access. Camera access is opt-in:
start the session with `enableScreenshots: true` (in `ARView.create()`
or the engine's `startSession()`) — `lightEstimation` no longer
requests it. Even with the opt-in, a browser may not grant the
feature, so screenshots stay best-effort: branch on `result.success`
and hide the feature when it fails. See
[Screenshots](/docs/guides/screenshots).

## An awaited `hitTest` never resolves after the user exits AR

Fixed in 1.1.0: the fallback hit-test promise settles when the session
ends (resolving `{hit: false, error: 'SESSION_ENDED'}`) and races a
one-second timeout as a backstop, so it cannot hang. In v1.0.0 it
resolved only from an animation-frame callback and hung if the session
ended first — the timeout-race workaround is no longer needed.

## `npx cap sync` didn't register the Android plugin

The package lacks the `capacitor` metadata key that drives automatic
discovery. Add the plugin to your Android project's `settings.gradle`
by hand, as the example does — full details in
[Capacitor setup](/docs/getting-started#capacitor-setup).

## Importing the package in a non-React app fails

The entry point re-exports the React hook, which imports React at module
top level, and React is only a peer dependency. Until the hook moves to a
subpath export, install `react` (and `react-dom` if your bundler asks)
even for plain-JS consumers.

## A second native `startSession` shows a session but no rendering

On the native path the render loop's paused flag is only cleared by an
activity-resume path that is never invoked, so after a stop the loop may
not restart within the same app run. Restarting the app clears it. This
is a known native lifecycle issue — see
[Known issues](/docs/known-issues).
