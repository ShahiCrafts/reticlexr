Thanks for contributing to reticlexr.

## Development

1. Fork the repository and create a focused branch from `main`.
2. Install the SDK dependencies with `npm install`.
3. Install the example app dependencies with `cd example && npm install`.
4. Run the example with `npm run dev:https` when testing WebXR on a
   physical device.
5. Keep AR/WebXR/Three.js implementation details inside the SDK; the
   example app should consume the public API.
6. Run the available validation/build commands before opening a pull
   request.

## Repository layout

| Area | Path |
| --- | --- |
| JavaScript API (facade, WebXR engine, hook, gestures) | `src/` |
| Native Android plugin | `android/` |
| Example app | `example/` |
| Documentation site (this site) | `website/` |
| Markdown docs (API reference, installation) | `docs/` |

## Before you open a PR

Run the checks locally:

- `npm test`, the Vitest suite (24 files, 25 tests).
- `npm run check-types`, `tsc --checkJs` over the implementation
  and its hand-written declarations.
- `cd example && npm install && npm run build`, the example app
  build.

## What CI checks

The committed workflow (`.github/workflows/ci.yml`) defines two
jobs: a `js` job (install with `npm ci`, the type-check, the test
suite, a consumer smoke test, a non-blocking `npm audit`, and the
example build) and a `gradle-assemble` job (`cap sync` plus
`:reticlexr:assembleDebug`). The workflow has not yet had a
completed run, so the local checks above are the verification that
counts. For AR-specific changes, your PR description carries the
rest: include the device/browser details, what you ran, and what
you saw.

## Pull requests

Keep changes focused, describe user-visible behaviour, document public
API changes, and include device/browser details for AR-specific fixes.

## Versioning

This project follows Semantic Versioning. Breaking public API changes
require a major version increment.
