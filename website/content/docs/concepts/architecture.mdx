The package is a Capacitor plugin with **two independent AR runtimes**
behind **three JS API layers**. There is no build step: the published
entry is the raw ESM source, with hand-written TypeScript declarations
(`src/*.d.ts`) alongside it.

## The three JS layers

| Layer | Files | Sits on |
| --- | --- | --- |
| `ARCore` facade — session/hit-test/model methods plus a local event bus (`on()`), bridging native events lazily, on first subscription | `src/index.js` (13.4 KB) | Capacitor plugin named `ARCore` |
| `ARView` / `createARView` + functional helpers — single active model, transform state, texture registry, gesture wiring | `src/ar-view.js` (9.8 KB) | WebXR engine only |
| `useARCore` hook + `createARGestureController` | `src/hooks.js` (27.7 KB), `src/gestures.js` (4.7 KB) | WebXR engine only |

The high-level layers **never call the native plugin**. If you use
`createARView` or the hook, you are on the WebXR runtime everywhere —
including inside a Capacitor app, where the WebView runs the same code.

## Data flow: JS → bridge → native ARCore

```
App JS ─ ARCore.startSession() ─ Capacitor bridge ─► ARCorePlugin (UI thread)
  ├─ camera permission check / request
  └─ ARSessionManager.createSession(planeDetection, lightEstimation)
       ├─ ArCoreApk availability / requestInstall
       ├─ new Session + Config (plane finding, light estimation, auto focus)
       └─ onSessionReady ─► ARRenderer + ARViewManager
            (native view inserted behind the WebView; WebView made transparent)

Render loop (dedicated ARRenderThread):
  Session.update() → tracking → planes → camera matrices
  → camera-texture background → Filament render

Events: managers → AREventEmitter → notifyListeners → Capacitor
  → the facade's lazily installed bridge → ARCore.on() subscribers

Hit test: JS hitTest({x, y}) → plugin → latest frame
  → normalised coords → display pixels → frame.hitTest()
```

## Data flow: JS → Three.js → WebXR

```
App ─ createARView({ overlay }) ─► ARView ─► ARCoreWeb
create() ─► setConfig() + startSession({ domOverlay })
  Three.js setup (once): WebGLRenderer, Scene, PerspectiveCamera (70°),
    lights, GLTFLoader, plane groups, reticle
  navigator.xr.requestSession('immersive-ar', {
    requiredFeatures: ['hit-test'],
    optionalFeatures: ['local-floor'?, 'plane-detection'?,
                       'light-estimation'?,
                       'camera-access'? (only with enableScreenshots),
                       'dom-overlay'? (with overlay)] })
  renderer.xr.setSession(); hit-test source from the viewer space;
  reference space: local-floor → local → viewer fallback chain

Per frame: viewer hit test → reticle pose + surface state
  (frame listeners notified on change, at most 10 Hz)
  every 8th frame: detected planes → dot/mesh visualisation
  anchor map → model + shadow transforms → render

Models: GLTFLoader.load(url) → cache → scene.clone() per placement
  → per-instance cloned materials → blob shadow plane per anchor
Gestures: Pointer Events on the overlay ─► facade callbacks ─► engine transforms
```

## The native side at a glance

Eleven Java classes under `android/src/main/java/com/capacitor/arcore/`:
the plugin facade, a session manager (sole owner of the ARCore
`Session`), a Filament renderer with its own render thread, a surface
manager, a coordinate mapper for hit tests, an event emitter, a view
manager — plus an anchor manager that registers the real anchors
created by hit tests, and a model manager that is currently a
registry only (native model rendering is not implemented). What
that means in practice is the subject of
[WebXR vs native ARCore](/docs/concepts/webxr-vs-native).
